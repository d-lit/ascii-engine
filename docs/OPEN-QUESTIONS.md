# Открытые вопросы

Сюда исполнитель записывает то, что не вправе решить сам. Архитектор отвечает и переносит итог в SPEC/DECISIONS. Закрытые вопросы не удаляются — помечаются `[закрыт]` со ссылкой на решение.

Формат:

```
## #N — Короткая формулировка
**Откуда:** задача NNN / фаза N, файл:строка
**Статус:** открыт | принято временно | закрыт
**Вопрос:** ...
**Варианты:** A — ..., B — ...
**Временное решение (если есть):** какой вариант и где в коде (TEMP-DECISION)
**Ответ архитектора:** ...
```

## #1 — Кто завершает renderer фазы 1 и подключение `main.ts`
**Откуда:** fallback фазы 1, ROADMAP:22–23
**Статус:** закрыт
**Вопрос:** `render/atlas.ts` и `render/canvas2d.ts` отсутствуют, а `main.ts` без них нельзя довести до рабочего импорта и отображения. Рендер относится к рискованным частям, которые по `CLAUDE.md` делает архитектор.
**Варианты:** A — архитектор реализует renderer, после чего делегирует механический `main.ts`; B — архитектор сначала оформляет отдельную точную задачу с внутренними структурами атласа и критериями производительности.
**Ответ архитектора:** Вариант A. Атлас и Canvas 2D — та часть, где ошибка стоит дорого: горячий цикл, стыковка тайлов, кэш по dpr. Описать её постановкой без архитектурных развилок не выйдет. После зелёного рендера `main.ts` становится механическим — контролы поверх готовых функций, это задача для Codex.

## #2 — Как измерять символы вне рампы при импорте текста
**Откуда:** fallback фазы 1, `src/core/import-text.ts:89`
**Статус:** закрыт → DECISIONS 008
**Вопрос:** SPEC требует измерять неизвестный символ тем же механизмом, что рампу. Текущий `importText` принимает опциональный callback и без него временно считает символ полностью плотным, поэтому поведение по умолчанию нарушает контракт.
**Варианты:** A — сделать измеритель обязательной зависимостью `importText`; B — передавать `FontSpec` и измерять внутри; C — ввести отдельный объект/сервис измерения плотности, общий для рампы и импорта.
**Ответ архитектора:** Вариант A. Вариант B втягивает canvas в `importText` и ломает тесты в окружении `node`; вариант C — лишний слой там, где достаточно функции. Измеритель становится обязательным параметром, canvas-реализация живёт в `ramp.ts` рядом с `measureRamp` и делит с ней кэш. Сигнатуры — DECISIONS 008, SPEC §3.2 и §4.

## #3 — Как определять широкие и комбинируемые Unicode-символы
**Откуда:** fallback фазы 1, `src/core/import-text.ts:35`
**Статус:** закрыт → DECISIONS 009
**Вопрос:** Текущие вручную заданные диапазоны неполны. Корректная ширина Unicode не определяется одним непрерывным диапазоном.
**Варианты:** A — поддерживать собственную таблицу East Asian Width и combining ranges; B — использовать `Intl.Segmenter` для графем плюс собственную таблицу ширины; C — согласовать небольшую dev/runtime-зависимость для Unicode width.
**Ответ архитектора:** Вариант B. Полная таблица East Asian Width — килобайты данных, которые придётся обновлять вслед за Unicode, ради сетки символов. `Intl.Segmenter` есть и в браузере, и в Node, и решает ту часть, которая действительно сложна: сборку графем (комбинируемые знаки, эмодзи, вариационные селекторы). Ширина остаётся коротким списком диапазонов. Подробности — DECISIONS 009, SPEC §3.2.

## #4 — Как гарантировать плотность процедурных оттенков на любом размере тайла
**Откуда:** fallback фазы 1, `src/render/block-glyphs.ts:28`
**Статус:** закрыт → DECISIONS 010
**Вопрос:** Матрица Bayer 4×4 даёт 25/50/75% только на размерах, равномерно покрывающих период. На маленьких и не кратных четырём тайлах фактическая плотность отличается от аналитической.
**Варианты:** A — выбирать точное число физических пикселей из упорядоченной матрицы размера тайла; B — сохранить периодический узор и задать минимальный/кратный четырём физический размер тайла; C — явно принять небольшое расхождение между аналитической и фактической плотностью.
**Ответ архитектора:** Вариант A. Вариант B навязывает рендеру размер ячейки из-за деталей растеризации — не та зависимость, которую стоит заводить. Вариант C оставляет аналитические плотности неправдой, а на них держится квантование. Рисуем ровно `round(d * w * h)` пикселей, выбирая их в порядке Bayer: узор сохраняется, плотность точна при любом размере. Цена нулевая — глифы растеризуются один раз в атлас. Подробности — DECISIONS 010, SPEC §9.3.

**Откуда:** fallback фазы 1, `docs/DECISIONS.md:44`
**Статус:** закрыт
**Вопрос:** Решение 001 всё ещё утверждает, что полярность учитывается только в квантователе, тогда как решение 004 добавило импорт текста.
**Варианты:** A — оставить исторический текст и добавить заметку «уточнено решением 004»; B — переписать решение 001 в актуальной формулировке.
**Ответ архитектора:** Вариант A. DECISIONS — журнал, а не справочник: запись фиксирует, что мы думали на тот момент, и переписывание задним числом стирает причину, по которой появилось решение 004. Добавлена пометка со ссылкой.
